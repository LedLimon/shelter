# Работа над задачей

Аргумент: номер задачи (`42`) или `next` — взять следующую доступную.

## 1. Выбрать и прочитать задачу

- Если передан `next`: найди открытые задачи с меткой `agent-ready` в самой ранней открытой вехе, без исполнителя и без открытых блокирующих задач:
  ```bash
  gh issue list -R LedLimon/shelter --label agent-ready --state open --json number,title,milestone,assignees,labels --limit 100
  ```
  Предпочитай `P0` → `P1` → `P2`. Покажи пользователю выбранную задачу одной строкой и продолжай.
- Прочитай задачу полностью, включая комментарии:
  ```bash
  gh issue view <N> -R LedLimon/shelter --comments
  ```
- Если у задачи метка `needs-human`, `idea` или `epic` — **остановись** и скажи, что это не задача для агента.

## 2. Проверить зависимости

- Блокирующие задачи — раздел «Зависимости» в теле и связи «blocked by»:
  ```bash
  gh api repos/LedLimon/shelter/issues/<N>/dependencies/blocked_by --jq '.[] | "\(.number) \(.state) \(.title)"'
  ```
- Если хоть одна блокирующая задача открыта — **остановись**, перечисли их и предложи взять одну из них.

## 3. Собрать контекст

- Прочитай `AGENTS.md` (если ещё не в контексте) и все документы из раздела «Документация» задачи.
- Для задач с меткой `money-critical` — обязательно `docs/ledger.md` и `docs/payments.md`.
- Посмотри существующий код в затрагиваемых модулях: переиспользуй утилиты, следуй принятым паттернам.
- Для UI-задач — `docs/design.md` целиком (направление «Объявление» из DS-0 и раздел «Отличие от шаблонных ИИ-сайтов»), [ADR-0006](../../../docs/adr/0006-visual-direction.md) и `docs/ai-tooling.md`. Компоненты shadcn/ui ищи и добавляй через shadcn MCP, а не по памяти. Документацию библиотек сверяй через context7 или `node_modules/next/dist/docs/`.
- Если требования неясны или противоречат docs — задай вопрос пользователю (или комментарием в задаче), предложив вариант по умолчанию. Не додумывай молча.

## 4. Ветка и реализация

```bash
git switch main && git pull --ff-only
git switch -c <type>/<N>-<short-slug>    # feat/42-need-status-machine
```

- Назначь задачу на себя, если работаешь от имени пользователя: `gh issue edit <N> -R LedLimon/shelter --add-assignee @me`.
- Реализуй по критериям приёмки. Маленькие коммиты в стиле Conventional Commits на английском.
- Пиши тесты вместе с кодом (см. `docs/testing.md`). Для денег — конкурентность и идемпотентность обязательны.
- Новый экран или крупный блок UI — сначала `/impeccable shape <экран>`: план UX и композиции до кода, в рамках направления из `docs/design.md`. Новое визуальное направление не выбирай: оно зафиксировано в `docs/design.md#визуальный-стиль`.
- React/Next.js-код пиши с учётом скилла `vercel-react-best-practices` (водопады запросов, размер бандла, лишние ре-рендеры). Ошибки рантайма и маршруты смотри через next-devtools MCP при запущенном `pnpm dev`.
- Отдельную найденную проблему не чини в этом PR — заведи задачу скиллом `new-issue`.

## 5. Проверки

Запусти всё, что уже есть в `package.json`:

```bash
pnpm format:check && pnpm typecheck && pnpm lint && pnpm test
pnpm e2e        # если задача затрагивает пользовательский сценарий
```

Если меняется UI:

1. Открой страницу в браузере (встроенный браузер, Playwright MCP или chrome-devtools MCP) и проверь mobile 375 px и desktop, светлую и тёмную тему.
2. `/impeccable polish <экран>` — финальный проход: выравнивание по дизайн-системе, отступы, состояния, детали браузера.
3. `/impeccable harden <экран>` — ошибки, пустые и загрузочные состояния, длинные русские тексты, переполнение.
4. Снова `pnpm format:check && pnpm typecheck && pnpm lint && pnpm test`, если polish/harden меняли код.

`/impeccable init` и выбор визуального направления не запускай — они прошли в DS-0. `document` — только после DS-1 и по задаче, которая это предусматривает. `npx impeccable install`/`update` не запускай: версия закреплена в `.claude/settings.json`.

## 6. Ревью субагентами

- Всегда: субагент `code-reviewer` на диффе `git diff main...HEAD`.
- Если метка `money-critical` или дифф трогает `src/server/ledger`, `src/server/payments`, денежные модели в `prisma/`, вебхуки — субагент `ledger-auditor`.
- Если менялся UI — субагент `ui-reviewer`: передай номер задачи, адреса изменённых страниц на запущенном `pnpm dev` и список изменённых UI-файлов. Production-сборку для замера производительности он поднимает сам.

Исправь найденное. Спорные замечания — вынеси в описание PR.

## 7. Pull request

```bash
git push -u origin HEAD
gh pr create -R LedLimon/shelter --fill-first --body-file <файл с телом по шаблону .github/pull_request_template.md>
```

- В теле обязательно `Closes #<N>`, что сделано, как проверено, скриншоты для UI.
- Отметь в чек-листе задачи выполненные пункты, если это уместно.
- Сообщи пользователю ссылку на PR и что осталось проверить человеку (для `money-critical` — обязательное ревью человека).
