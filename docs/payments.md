# Платежи (CloudPayments)

Провайдер — **CloudPayments** ([ADR-0002](adr/0002-cloudpayments.md)), за интерфейсом `PaymentProvider` (`src/server/payments`). Для dev и CI — `FakeCloudPayments` и симулятор подписанных вебхуков. Учёт денег — [ledger.md](ledger.md).

> Форматы вебхуков, виджета и API сверены с документацией CloudPayments при реализации платёжного слоя — что именно и что осталось проверить на тестовом терминале, см. [«Сверка с документацией»](#сверка-с-документацией-cloudpayments). Тарифы и доступность СБП для рекуррентов уточняются при подключении (ORG-2).

## Платёжный слой

Код — [`src/server/payments`](../src/server/payments). Остальные домены знают только интерфейс `PaymentProvider` и доменные типы из `types.ts`: суммы — целые копейки, время — `Date`, полей CloudPayments снаружи модуля нет. Так провайдера можно заменить (ЮKassa — [ADR-0002](adr/0002-cloudpayments.md)) и целиком эмулировать.

| Метод                                                 | Что делает                                                                                                                                                                                         |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `widgetParams(intent)`                                | Что нужно браузеру, чтобы начать оплату: параметры виджета CloudPayments (`kind: "cloudpayments"`) или адрес страницы оплаты (`kind: "redirect"` — эмулятор, в будущем провайдеры с редиректом)    |
| `verifyWebhook({ rawBody, headers })`                 | Подписан ли вебхук провайдером. Вызывается первым, по сырому телу (`await request.text()`); без подписи — ответ 401, тело дальше не читается                                                       |
| `parseWebhook(type, rawBody)`                         | Событие `check` / `pay` / `fail` / `refund` / `recurrent` в доменных типах, с готовым `dedupeKey`. Бросает `WebhookParseError`, если тело не такое, как в документации, или мы такого не принимаем |
| `refund({ providerTxId, amountKop, idempotencyKey })` | Запрос возврата. Движение денег подтверждает вебхук `refund`                                                                                                                                       |
| `cancelSubscription` / `updateSubscription`           | Отмена подписки и смена суммы                                                                                                                                                                      |
| `listTransactions({ from, to })`                      | Реестр операций за период `[from, to)` с комиссиями — для сверки и импорта комиссий                                                                                                                |

Провайдер выбирает переменная `PAYMENT_PROVIDER`; в приложении его отдаёт `getPaymentProvider()` из `@/server/payments`, воркеру — `createPaymentProvider(env)` (без `server-only`).

- `cloudpayments` — адаптер CloudPayments; нужны `CLOUDPAYMENTS_PUBLIC_ID` и `CLOUDPAYMENTS_API_SECRET`. Так настроены staging (тестовый терминал) и production.
- `fake` (по умолчанию) — [эмулятор](#эмулятор-fakecloudpayments) для dev и CI. Он ничего не списывает, поэтому сервер с ним запускается, только если `APP_URL` — этот компьютер (`localhost`, `*.localhost`, `127.0.0.1`). На публичном адресе без ключей CloudPayments сервер не стартует — «бесплатно оплатить» на настоящем сайте нельзя.

### Правила для обработчиков

1. **Сначала подпись, потом разбор.** `verifyWebhook` → `parseWebhook`. Подпись — HMAC-SHA256 тела в base64 с ключом API Secret, сравнение за постоянное время. Проверяется заголовок `Content-HMAC`: он посчитан по телу как оно пришло. `X-Content-HMAC` CloudPayments считает по раскодированным параметрам — его пришлось бы воспроизводить догадками, поэтому он не используется.
2. **`WebhookParseError` — это ошибка, а не «принято».** Отвечаем ненулевым кодом: CloudPayments повторит уведомление (до 100 раз), а мы увидим его в журнале. Сообщение ошибки называет поля, но не значения: в теле есть email.
3. **Читаются только нужные поля.** Новое или изменившееся поле, которое нам не нужно (карта, комиссия в Pay, геоданные), платёж не сломает. Нужные — строго: сумму или дату, которые не читаются точно, не угадываем.
4. **Не принимаются:** валюта кроме `RUB` (сумму в другой валюте нельзя прочитать как рубли); двухстадийный платёж — `Status: Authorized` (деньги только заблокированы и вернутся донору, а мы платежи не подтверждаем); выплаты на карту.
5. **`fail` бывает и про возврат.** У события есть `operation`: неудачный возврат (`refund`) не должен пометить пожертвование как несостоявшееся.
6. **`metadata` прошла через браузер донора.** Проверяем её схемой и не доверяем ей больше, чем своим записям. Email и сумма в вебхуке — тоже от провайдера, а не из нашей базы: сумму сверяет `check`.
7. **`testMode`** — платёж тестового терминала, настоящих денег нет. На staging это норма; в production такой платёж не должен попасть в книгу (решается в PAY-3).
8. **API провайдера — вне транзакции БД.** Ошибка — `PaymentProviderError`. `REJECTED`, `UNAUTHORIZED`, `RATE_LIMITED`, `INVALID_INPUT` — операция точно не выполнена. `UNAVAILABLE` и `BAD_RESPONSE` (`outcomeUnknown`) — неизвестно: возврат мог пройти. Тогда запрос повторяют с тем же ключом или ищут операцию в реестре, но не записывают как неудачную.
9. **Идемпотентность запросов к API — наша.** Ключ `refund:{donationId}:{n}` уходит в заголовке `X-Request-ID`, но CloudPayments помнит ответ только час. Поэтому возврат сначала записывается у нас, а заголовок страхует лишь от сетевых повторов.
10. **`subscriptions/update` реактивирует отменённую или завершённую подписку.** Перед сменой суммы проверяем статус у себя. После изменения через API уведомление `recurrent` не приходит — подписку возвращает сам ответ.

### Настройки терминала в личном кабинете

- Уведомления Check, Pay, Fail, Refund, Recurrent — на `https://<сайт>/api/webhooks/cloudpayments/{check|pay|fail|refund|recurrent}`.
- **HTTP-метод — POST** (по умолчанию в кабинете GET), **кодировка — UTF-8**, **формат — CloudPayments**. Другие форматы адаптер не читает.
- Схема оплаты — одностадийная.

### Эмулятор FakeCloudPayments

`PAYMENT_PROVIDER=fake`. «Виджет» — страница нашего же сайта: `/fake-cloudpayments/checkout/[id]`, куда ведёт `widgetParams()`. На ней выбирают исход — оплата, отказ банка, 3-D Secure (и затем верный или неверный код), закрыть без оплаты, — и эмулятор отправляет на `/api/webhooks/cloudpayments/{type}` такие же подписанные уведомления, как CloudPayments: тот же формат тела, те же заголовки, а проверяет и разбирает их тот же код, что и настоящие. Страница показывает, что ответил сайт на каждое уведомление, и возвращает донора на `returnUrl`.

- **Check — как в кабинете.** С включённой галочкой «Отправлять уведомление Check» платёж проходит, только если сайт ответил на Check `{"code":0}`; иначе он отклонён — так же поступает CloudPayments. Пока обработчика вебхуков нет (PAY-3), успешная оплата возможна только со снятой галочкой.
- **Тестовый платёж без формы доната** — `/fake-cloudpayments`: сумма, почта, «ежемесячно».
- **API** эмулируется в памяти: `refund` отправляет уведомление Refund и не даёт вернуть больше оплаченного, повтор с тем же ключом возвращает первый ответ; `cancelSubscription` отправляет Recurrent со статусом `Cancelled`; `updateSubscription` меняет сумму и, как CloudPayments, реактивирует подписку; `listTransactions` отдаёт операции с условной комиссией 2,9 %.
- **Память, а не база.** Перезапуск сервера забывает платежи и подписки эмулятора. Возврат по платежу, которого эмулятор уже не помнит, проходит без проверки суммы — чтобы старая dev-база оставалась рабочей. Номера транзакций не повторяются между перезапусками.
- **Чего эмулятор не делает:** не повторяет недоставленные уведомления и не списывает по подписке сам. Очередные списания и смену статусов подписки в тестах задаёт [симулятор вебхуков](testing.md#платежи-в-тестах); кнопки для dev появятся вместе с подписками (PAY-5).
- Страницы эмулятора отвечают 404, если провайдер настоящий.

### Сверка с документацией CloudPayments

Сверено с [developers.cloudpayments.ru](https://developers.cloudpayments.ru/) 11.10.2026:

- **Уведомления** Check, Pay, Fail, Refund, Recurrent: состав и форматы полей (`Amount` — рубли с точкой, до двух знаков; `DateTime` — `yyyy-MM-dd HH:mm:ss` в UTC; `TestMode` — `1`/`0`; `Data` — JSON), ожидаемый ответ `{"code":0}`, коды отказа в Check (10, 11, 12, 13, 20), повторы (100 попыток, тайм-аут 30 с), статусы подписок (`Active`, `PastDue`, `Cancelled`, `Rejected`, `Expired`), коды отказов (5051, 5206).
- **Подпись:** заголовки `Content-HMAC` и `X-Content-HMAC`, SHA-256, UTF-8, ключ — API Secret, base64; сообщение для POST — тело запроса.
- **Виджет:** запускается как `new cp.CloudPayments().start({...})`. Параметры переименованы: `publicTerminalId`, `externalId` (бывший `invoiceId`), `metadata` (бывший `data`), `userInfo.accountId` и `userInfo.email`, `recurrent` верхнего уровня, `paymentSchema: "Single"`. В уведомлениях они по-прежнему приходят как `InvoiceId`, `Data`, `AccountId`.
- **API:** HTTP Basic (логин — Public ID, пароль — API Secret), `X-Request-ID` (результат хранится час), `payments/refund`, `subscriptions/cancel`, `subscriptions/update`, `v2/payments/list` (страницы по 100, от старых к новым), ответ `{ Success, Message, Model }`.

Чего в документации нет — **проверить на тестовом терминале (ORG-2)**; фикстуры вебхуков в `tests/fixtures/` пока составлены по таблицам документации, а не сняты с настоящих запросов:

- `Content-Type` уведомлений в формате «CloudPayments» (ждём `application/x-www-form-urlencoded`);
- приходит ли `recurrent` после отмены подписки через API (эмулятор отправляет — обработчик должен выдержать оба варианта);
- число `Type` у возврата в реестре (в примерах: `0` — оплата, `2` — выплата; `1` для возврата — по порядку справочника);
- какой email приходит в поле `Email` (из `userInfo.email` или введённый в виджете) и какие поля пусты у платежа по СБП;
- принимает ли `X-Request-ID` произвольную строку (адаптер на всякий случай отправляет UUID, вычисленный из нашего ключа);
- поведение `successRedirectUrl` / `failRedirectUrl` вместе с промисом `start()`.

## Разовое пожертвование

1. **Форма** (см. [product.md](product.md#пожертвования)) → server action `createDonationIntent`:
   - zod-валидация, rate limit, минимальная сумма;
   - проверка, что нужда в статусе `COLLECTING` (иначе — предложить общий фонд);
   - создать `Donation(PENDING)` и `ConsentRecord` (версии документов);
   - вернуть параметры виджета — `getPaymentProvider().widgetParams(intent)`: `invoiceId = donation.id`, сумма, email, `metadata` (target, needId), `returnUrl` — страница статуса.
2. **Вебхук `check`** `/api/webhooks/cloudpayments/check`:
   - проверить HMAC по сырому телу (`await req.text()`);
   - проверить, что invoice существует и сумма совпадает;
   - ответ `{ code: 0 }` или отказ. **Не** отказывать из-за закрытой нужды — это решает правило переплаты.
3. **Вебхук `pay`**:
   - проверить HMAC;
   - вставить `WebhookEvent` с `dedupeKey = cp:pay:{TransactionId}`; если уже есть — ответить `{ code: 0 }`;
   - выполнить транзакцию распределения ([ledger.md#переплата](ledger.md#переплата));
   - ответить `{ code: 0 }`. При исключении — ненулевой код, чтобы CloudPayments повторил; ошибка видна в `/admin/webhooks` с кнопкой повтора.
   - Если invoice неизвестен (вебхук пришёл раньше коммита intent) — создать `Donation` из `metadata` события (поле `Data` вебхука).
4. **Вебхук `fail`** — `Donation → FAILED`, без проводок.
5. **Страница статуса** `/donate/status/[id]` опрашивает `/api/donations/[id]/status` и не доверяет редиректу.

## Ежемесячные пожертвования и опека

- **Первый платёж** — intent с `recurrent: { interval: "MONTH", period: 1 }` и `accountId` (без него CloudPayments подписку не создаёт). Вебхук Pay содержит `SubscriptionId` → upsert `Subscription`, письмо со ссылкой управления (токен; в БД — только хэш).
- **Следующие списания** — Pay с `SubscriptionId` → новый `Donation(source = RECURRING)` → общий фонд (для опеки — с `dogId`, влияет на шкалу покрытия собаки).
- **Неудачное списание** (Fail): Donation → FAILED, `failedCount++`, подписка → `PAST_DUE`, донору — письмо «обновите карту» (создаётся новая подписка с `replacesId`, т.к. сменить карту в существующей нельзя).
- **Вебхук `recurrent`** (Cancelled / Rejected / Expired): обновить статус, одно письмо донору, уведомить куратора (для опеки), пересчитать покрытие.
- **Отмена** (кабинет или токен-ссылка): сначала API провайдера, `CANCELLED` — только после подтверждения; при ошибке API — повтор через очередь. Списание, пришедшее после отмены, — автоматический возврат.
- **Смена суммы** — `updateSubscription` (`subscriptions/update`). Только для активной подписки: CloudPayments реактивирует отменённую при любом изменении.
- **Напоминание** за 3 дня до списания.
- Согласие на рекуррент — отдельная неотмеченная галочка с суммой и периодичностью ([legal.md](legal.md)).

## Возвраты и чарджбэки

- Инициирует админ через API с ключом идемпотентности `refund:{donationId}:{n}`. Вебхук Refund → проводка `REFUND`. Ключ провайдер помнит только час ([правила](#правила-для-обработчиков), п. 8–9): возврат сначала записывается у нас.
- Откуда списывается: со счёта нужды, если она ещё не `IN_PROGRESS`/`DONE`; иначе — из общего фонда.
- Нужда в `COLLECTED`, по которой ещё ничего не купили, может вернуться в `COLLECTING` (запись в аудит и таймлайн).

## Комиссии и сверка

- **Комиссии** — ежедневный импорт из реестра провайдера как `FEE` (общий фонд → FEES_OUT). Нужды показывают валовую сумму. Опция «покрыть комиссию» добавляет к сумме доната расчётную комиссию.
- **Ежедневная сверка**: список транзакций провайдера vs наши `Donation`; пропущенные прогоняются через тот же обработчик (идемпотентно).
- **Тревоги**: ошибки вебхуков, расхождения сверки, всплеск отказов (возможный кардинг) — в админ-дашборд и уведомление сотрудникам.

## Крайние случаи

1. **Порядок вебхуков**: Pay раньше intent — создать Donation из payload; Refund раньше Pay — `DEFERRED` и повтор.
2. **Сумма в вебхуке ≠ intent** — принять фактическую, записать, пометить на проверку.
3. **Нужду закрыли, пока донор платил** — вся сумма в общий фонд, письмо с объяснением.
4. **Нужду отменили** — `CANCEL_TO_GENERAL`, бережное письмо донорам.
5. **Собаку забрали / умерла при активной опеке** — уведомить опекунов, подписка → общий фонд, если не отказались. Собаку не удалять.
6. **Возврат после закупки** — из общего фонда.
7. **Поздний вебхук за закрытый месяц** — проводка в текущем месяце с пометкой периода.
8. **Кардинг** — минимум ~100 ₽, rate limit, Yandex SmartCaptcha при всплеске отказов.
9. **Опечатка в email гостя** — повтор email в форме; поддержка находит подписку в кабинете CloudPayments по маске карты.
10. **Привязка истории к аккаунту** — только после подтверждения email.
11. **Дедлоки** — блокировки строго `Donation → Need → Subscription`, последней — блокировка периода книги ([ledger.md](ledger.md#инварианты)).
