# Платежи (CloudPayments)

Провайдер — **CloudPayments** ([ADR-0002](adr/0002-cloudpayments.md)), за интерфейсом `PaymentProvider` (`src/server/payments`). Для dev и CI — `FakeCloudPayments` и симулятор подписанных вебхуков. Учёт денег — [ledger.md](ledger.md).

> Форматы вебхуков, виджета и API сверены с документацией CloudPayments при реализации платёжного слоя — что именно и что осталось проверить на тестовом терминале, см. [«Сверка с документацией»](#сверка-с-документацией-cloudpayments). Тарифы и доступность СБП для рекуррентов уточняются при подключении (ORG-2).

## Платёжный слой

Код — [`src/server/payments`](../src/server/payments). Остальные домены знают только интерфейс `PaymentProvider` и доменные типы из `types.ts`: суммы — целые копейки, время — `Date`, полей CloudPayments снаружи модуля нет. Так провайдера можно заменить (ЮKassa — [ADR-0002](adr/0002-cloudpayments.md)) и целиком эмулировать.

| Метод                                                 | Что делает                                                                                                                                                                                      |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `widgetParams(intent)`                                | Что нужно браузеру, чтобы начать оплату: параметры виджета CloudPayments (`kind: "cloudpayments"`) или адрес страницы оплаты (`kind: "redirect"` — эмулятор, в будущем провайдеры с редиректом) |
| `receiveWebhook(type, { rawBody, headers })`          | Событие входящего вебхука: сначала подпись по сырому телу (`await request.text()`), потом разбор. Бросает `WebhookSignatureError` (ответ 401, больше ничего не делать) или `WebhookParseError`  |
| `parseStoredWebhook(type, rawBody)`                   | Событие из тела, которое уже прошло `receiveWebhook` и лежит в журнале (повторная обработка). Подпись не проверяет — не для входящих запросов                                                   |
| `webhookResponse(reply)`                              | HTTP-ответ провайдеру: `"ok"`, отказы для Check (`"unknown-invoice"`, `"wrong-amount"`, `"declined"`, `"expired"`) или `"retry"` — «не обработали, пришлите ещё раз»                            |
| `refund({ providerTxId, amountKop, idempotencyKey })` | Запрос возврата. Движение денег подтверждает вебхук `refund`                                                                                                                                    |
| `cancelSubscription`, `getSubscription`               | Отмена подписки; подписка, как она сейчас у провайдера                                                                                                                                          |
| `updateSubscription({ subscriptionId, amountKop })`   | Смена суммы — только у подписки, которая ещё списывает (`ACTIVE`, `PAST_DUE`); иначе `REJECTED`                                                                                                 |
| `listTransactions({ from, to })`                      | Реестр операций за период `[from, to)` с комиссиями: `{ transactions, testTransactions, unreadable }`                                                                                           |
| `acceptsTestPayments`                                 | Считаются ли здесь платежи тестового терминала (staging, dev)                                                                                                                                   |

Провайдер выбирает переменная `PAYMENT_PROVIDER`; в приложении его отдаёт `getPaymentProvider()` из `@/server/payments`, воркеру — `createPaymentProvider(env)` (без `server-only`).

- `cloudpayments` — адаптер CloudPayments; нужны `CLOUDPAYMENTS_PUBLIC_ID` и `CLOUDPAYMENTS_API_SECRET`. Так настроены staging (тестовый терминал, `CLOUDPAYMENTS_ACCEPT_TEST_PAYMENTS=true`) и production.
- `fake` — [эмулятор](#эмулятор-fakecloudpayments) для dev и CI. Он ничего не списывает, поэтому на настоящий сайт его не пускает проверка окружения:
  - сервер с ним запускается, только если `APP_URL` — этот компьютер (`localhost`, `*.localhost`, `127.0.0.1`); на публичном адресе без ключей CloudPayments сервер не стартует;
  - по умолчанию (переменная пуста) он включается только в разработке и тестах — production-сборка (`NODE_ENV=production`) требует назвать провайдера явно.

  Сверх этого — страховка от случайного посетителя, а не защита: страницы эмулятора и приём его вебхуков отвечают отказом на запрос, адресованный не этому компьютеру (публичное имя, адрес в локальной сети). Прокси, который подменяет `Host`, её обходит.

### Правила для обработчиков

1. **Сначала подпись, потом разбор** — это один вызов `receiveWebhook`. Подпись — HMAC-SHA256 тела в base64 с ключом API Secret, сравнение за постоянное время. Проверяется заголовок `Content-HMAC`: он посчитан по телу как оно пришло. `X-Content-HMAC` CloudPayments считает по раскодированным параметрам — его пришлось бы воспроизводить догадками, поэтому он не используется.
2. **Тип берётся из адреса, а подпись адрес не покрывает.** Подписанный Check, отправленный на `/pay` (ошибка в кабинете, повтор из журнала), не должен стать платежом: Check приходит до ответа банка, и платёж может быть отклонён. Поэтому в Pay обязателен `GatewayName` — по документации он есть в Pay и его нет в Check (**проверить на тестовом терминале до приёма денег**, см. ниже). В обратную сторону: Pay на адресе Check отклоняется, если в нём есть код авторизации `AuthCode` — до ответа банка его быть не может. Pay без `AuthCode` на адресе Check пройдёт как Check и ничего не запишет; такой перепутанный адрес ловят первый тестовый платёж и сверка. Из-за лишнего поля Check не отклоняем: отказ на Check — это отклонённый платёж. Но если в Check пришёл `GatewayName`, признак Pay перестал работать — событие несёт `hasPayMarker: true`, и обработчик должен поднять тревогу (платёж при этом пропускаем).
3. **`WebhookParseError` — это ошибка, а не «принято».** Отвечаем `webhookResponse("retry")`: CloudPayments повторит уведомление (до 100 раз), а мы увидим его в журнале. Сообщение ошибки называет поля, которые мы читаем, но не значения и не то, что пришло в теле: там email.
4. **Читаются только нужные поля.** Новое, изменившееся или повторённое поле, которое нам не нужно (карта, комиссия в Pay, геоданные, `CustomFields`), платёж не сломает. Нужные — строго: сумму или дату, которые не читаются точно, не угадываем; повтор нужного поля — ошибка.
5. **Не принимаются:** валюта кроме `RUB` (сумму в другой валюте нельзя прочитать как рубли); двухстадийный платёж — `Status: Authorized` (деньги только заблокированы и вернутся донору, а мы платежи не подтверждаем); выплаты на карту; **тестовые платежи** (`testMode`) в Check и Pay, если провайдер их не принимает (`acceptsTestPayments`). Тестовый платёж — не деньги: в production он не должен попасть в книгу, даже если терминал по ошибке остался в тестовом режиме. В реестре такие операции лежат отдельно — в `testTransactions`, а не в `transactions`.
6. **Отказ не окончателен.** `fail` — отказ по этой транзакции, а не по счёту: виджет даёт «Повторить платёж» (`retryPayment`), а CloudPayments может сам повторить через резервный банк. После `fail` может прийти `pay` с тем же `invoiceId` и другим `providerTxId` — его нужно провести, а опоздавший `fail` первой транзакции не должен отменить успех (сверяем `providerTxId`). `pay` — факт: деньги списаны, в каком бы статусе ни было пожертвование.
7. **`fail` и `check` бывают про возврат.** У события есть `operation`: неудачный возврат (`refund`) не должен пометить пожертвование как несостоявшееся.
8. **`metadata` прошла через браузер донора** и может быть чем угодно (массив, число, ключ `__proto__`). Проверяем её схемой, не сливаем с объектами и не доверяем ей больше, чем своим записям. Email и сумма в вебхуке — тоже от провайдера, а не из нашей базы: сумму сверяет `check`.
9. **Дедупликация — по `dedupeKey`, строки журнала не удаляются.** В подписи нет времени: от повтора старого Pay защищает только то, что его ключ уже есть. Check по ключу не «коротим» (отказ на повторе не должен стать согласием). У `recurrent` своего id нет — ключ считается по телу, поэтому два изменения с одинаковым телом неразличимы: применяем событие как снимок состояния подписки, а ключ бережёт от второго письма.
10. **API провайдера — вне транзакции БД.** Ошибка — `PaymentProviderError` с полем `outcome`. `"not-performed"` — операция точно не выполнена. `"unknown"` (нет ответа, нечитаемый ответ) — возврат мог пройти: не записывать как неудачный.
11. **Идемпотентность запросов к API — наша.** Ключ `refund:{donationId}:{n}` уходит в заголовке `X-Request-ID`, но CloudPayments помнит ответ **только час**. Поэтому возврат сначала записывается у нас. После неизвестного исхода в течение часа повторяем с тем же ключом; позже — только после поиска операции в реестре (`listTransactions`, `originalTxId`) или по вебхуку `refund`: повтор с забытым ключом — второй возврат. И наоборот, `REJECTED` на позднем повторе («сумма превышает платёж») не доказывает, что первая попытка не прошла.
12. **Подписку меняем только активную.** `subscriptions/update` у CloudPayments реактивирует отменённую или завершённую подписку — и начнёт списывать с донора, который отказался. `updateSubscription` перед изменением спрашивает статус у провайдера (донор мог отменить на my.cloudpayments.ru минуту назад) и отказывает, если подписка не списывает. После изменения через API уведомление `recurrent` не приходит — подписку возвращает сам ответ.
13. **`accountId` — наш непрозрачный идентификатор, не email:** он виден в кабинете провайдера и приходит в вебхуках.
14. **В реестре деньги — только `payment` со статусом `COMPLETED`** из `transactions`. Там же лежат отказы, возвраты и незавершённые операции; тестовые (где они не считаются) — в `testTransactions`: если список не пуст, терминал в тестовом режиме, и об этом должен узнать человек.
15. **Реестр не падает из-за одной строки.** Строки, которые не удалось прочитать, `listTransactions` отдаёт отдельно (`unreadable`: номер транзакции и имена полей): запись в реестре вечная, и иначе этот день не сверился бы никогда. Читаемое импортируем, по нечитаемым — тревога.

### Настройки терминала в личном кабинете

- Уведомления Check, Pay, Fail, Refund, Recurrent — на `https://<сайт>/api/webhooks/cloudpayments/{check|pay|fail|refund|recurrent}`. Адреса различаются одним словом — перепутанный адрес разбор отклонит (правило 2), но проверьте их глазами.
- **HTTP-метод — POST** (по умолчанию в кабинете GET), **кодировка — UTF-8**, **формат — CloudPayments**. Другие форматы адаптер не читает.
- Схема оплаты — одностадийная.
- В production терминал — боевой; пока он тестовый, сайт не примет ни одного платежа (и это правильно).

### Эмулятор FakeCloudPayments

`PAYMENT_PROVIDER=fake`. «Виджет» — страница нашего же сайта: `/fake-cloudpayments/checkout/[id]`, куда ведёт `widgetParams()`. На ней выбирают исход — оплата, отказ банка, 3-D Secure (и затем верный или неверный код), закрыть без оплаты, после отказа — «Повторить платёж», — и эмулятор отправляет на `/api/webhooks/cloudpayments/{type}` такие же подписанные уведомления, как CloudPayments: тот же формат тела, те же заголовки, а проверяет и разбирает их тот же код, что и настоящие. Страница показывает, что ответил сайт на каждое уведомление — исход считается успешным, только если сайт принял Pay, — и возвращает донора на `returnUrl`.

- **Check — как в кабинете.** С включённой галочкой «Отправлять уведомление Check» платёж проходит, только если сайт ответил на Check `{"code":0}`; иначе он отклонён — так же поступает CloudPayments. Пока обработчика вебхуков нет (PAY-3), провести оплату можно только со снятой галочкой, а страница честно напишет, что сайт уведомление Pay не принял.
- **Тестовый платёж без формы доната** — `/fake-cloudpayments`: сумма, почта, «ежемесячно». При «Повторить платёж» виджет помнит, была ли включена галочка Check.
- **API** эмулируется в памяти и проверяет аргументы тем же кодом, что адаптер. `refund` отправляет уведомление Refund и не даёт вернуть больше оплаченного; повтор с тем же ключом возвращает первый ответ — в течение часа, потом это второй возврат, как у CloudPayments. `cancelSubscription` отправляет Recurrent со статусом `Cancelled`. `updateSubscription` меняет сумму активной подписки и отказывает для остальных. `listTransactions` отдаёт операции с условной комиссией 2,9 %.
- **Память процесса, а не база.** Перезапуск сервера забывает платежи и подписки эмулятора; у воркера (отдельный процесс) память своя, и о платежах веб-сервера он не знает. Возврат по платежу, которого эмулятор уже не помнит, проходит без проверки суммы — чтобы старая dev-база оставалась рабочей. Номера транзакций не повторяются между перезапусками.
- **Уведомления уходят на `APP_URL`** — он должен быть адресом этого же сервера (как и для входа сотрудников); страница показывает полный адрес каждой доставки. В тестах доставку перехватывает [симулятор](testing.md#платежи-в-тестах).
- **Чего эмулятор не делает:** не повторяет недоставленные уведомления и не списывает по подписке сам. Очередные списания и смену статусов подписки в тестах задаёт симулятор вебхуков; кнопки для dev появятся вместе с подписками (PAY-5).
- Страницы эмулятора отвечают 404, если провайдер настоящий или запрос адресован не этому компьютеру (открыть эмулятор с телефона по адресу в локальной сети не получится).

### Сверка с документацией CloudPayments

Сверено с [developers.cloudpayments.ru](https://developers.cloudpayments.ru/) 11.10.2026:

- **Уведомления** Check, Pay, Fail, Refund, Recurrent: состав и форматы полей (`Amount` — рубли с точкой, до двух знаков; `DateTime` — `yyyy-MM-dd HH:mm:ss` в UTC; `TestMode` — `1`/`0`; `Data` — JSON; в таблице Pay `GatewayName` обязателен, в таблице Check его нет), ожидаемый ответ `{"code":0}`, коды отказа в Check (10, 11, 12, 13, 20), повторы (100 попыток, тайм-аут 30 с), статусы подписок (`Active`, `PastDue`, `Cancelled`, `Rejected`, `Expired`), коды отказов (5051, 5206). Отказ не конечен: «пользователь может оплатить со второго раза».
- **Подпись:** заголовки `Content-HMAC` и `X-Content-HMAC`, SHA-256, UTF-8, ключ — API Secret, base64; сообщение для POST — тело запроса.
- **Виджет:** запускается как `new cp.CloudPayments().start({...})`. Параметры переименованы: `publicTerminalId`, `externalId` (бывший `invoiceId`), `metadata` (бывший `data`), `userInfo.accountId` и `userInfo.email`, `recurrent` верхнего уровня, `paymentSchema: "Single"`, `retryPayment` (по умолчанию `true`). В уведомлениях они по-прежнему приходят как `InvoiceId`, `Data`, `AccountId`.
- **API:** HTTP Basic (логин — Public ID, пароль — API Secret); `X-Request-ID` — любое значение на наш выбор, результат хранится час; `payments/refund`, `subscriptions/get`, `subscriptions/cancel`, `subscriptions/update` (реактивирует подписку), `v2/payments/list` (страницы по 100, от старых к новым), ответ `{ Success, Message, Model }`.

Чего в документации нет — **проверить на тестовом терминале (ORG-2)**; фикстуры вебхуков в `tests/fixtures/` пока составлены по таблицам документации, а не сняты с настоящих запросов:

- **тело настоящего Check, отправленное на адрес Pay, отклоняется** — прогнать матрицу «тело одного типа на адрес другого» (`webhooks.test.ts`) на снятых телах. Если в настоящем Check есть `GatewayName`, нужен другой признак, и до тех пор принимать платежи нельзя;
- `Content-Type` уведомлений в формате «CloudPayments» (ждём `application/x-www-form-urlencoded`);
- есть ли `GatewayName` в Pay по СБП — без него Pay не разберётся (в таблице он обязательный) — и нет ли `AuthCode` в Check; тестовый платёж сделать и картой, и по СБП, после каждого пожертвование должно стать оплаченным (так находится перепутанный адрес Pay);
- повторный `payments/refund` с тем же `X-Request-ID` (наш ключ вида `refund:{id}:{n}`) в пределах часа возвращает тот же `TransactionId`, а не делает второй возврат;
- несёт ли Pay первого платежа с `recurrent` поле `SubscriptionId` и приходит ли `recurrent` со статусом `Active` при создании подписки (эмулятор: `SubscriptionId` есть, `recurrent` при создании нет);
- приходит ли `recurrent` после отмены подписки через API (эмулятор отправляет — обработчик должен выдержать оба варианта) и одинаковы ли побайтно повторы одного `recurrent`;
- что лежит в `Data`, кроме нашей `metadata` (старый виджет добавлял туда свои ключи — схема должна терпеть лишнее);
- есть ли `Status` в Check операции возврата (адаптер не требует; поэтому Fail возврата, присланный на адрес Check, разберётся как Check — денег это не касается);
- число `Type` у возврата в реестре (в примерах: `0` — оплата, `2` — выплата; `1` для возврата — по порядку справочника; до проверки строка, где `Type` и ссылка на исходную транзакцию расходятся, уходит в `unreadable`);
- какой email приходит в поле `Email` (из `userInfo.email` или введённый в виджете) и какие поля пусты у платежа по СБП;
- поведение `successRedirectUrl` / `failRedirectUrl` вместе с промисом `start()`.

## Разовое пожертвование

1. **Форма** (см. [product.md](product.md#пожертвования)) → server action `createDonationIntent`:
   - zod-валидация, rate limit, минимальная сумма;
   - проверка, что нужда в статусе `COLLECTING` (иначе — предложить общий фонд);
   - создать `Donation(PENDING)` и `ConsentRecord` (версии документов);
   - вернуть параметры виджета — `getPaymentProvider().widgetParams(intent)`: `invoiceId = donation.id`, сумма, email, `metadata` (target, needId), `returnUrl` — страница статуса.
2. **Вебхук `check`** `/api/webhooks/cloudpayments/check`:
   - проверить HMAC по сырому телу (`await req.text()`);
   - проверить, что invoice существует и сумма совпадает;
   - ответ `{ code: 0 }` или отказ. **Не** отказывать из-за закрытой нужды — это решает правило переплаты.
3. **Вебхук `pay`**:
   - проверить HMAC;
   - вставить `WebhookEvent` с `dedupeKey = cp:pay:{TransactionId}`; если уже есть — ответить `{ code: 0 }`;
   - выполнить транзакцию распределения ([ledger.md#переплата](ledger.md#переплата));
   - ответить `{ code: 0 }`. При исключении — ненулевой код, чтобы CloudPayments повторил; ошибка видна в `/admin/webhooks` с кнопкой повтора.
   - Если invoice неизвестен (вебхук пришёл раньше коммита intent) — создать `Donation` из `metadata` события (поле `Data` вебхука).
4. **Вебхук `fail`** — `Donation → FAILED`, без проводок. Это не конец: донор может повторить оплату в том же виджете, и тогда придёт `pay` с другой транзакцией ([правила](#правила-для-обработчиков), п. 6).
5. **Страница статуса** `/donate/status/[id]` опрашивает `/api/donations/[id]/status` и не доверяет редиректу.

## Ежемесячные пожертвования и опека

- **Первый платёж** — intent с `recurrent: { interval: "MONTH", period: 1 }` и `accountId` (без него CloudPayments подписку не создаёт; наш непрозрачный идентификатор, не email). Вебхук Pay содержит `SubscriptionId` → upsert `Subscription`, письмо со ссылкой управления (токен; в БД — только хэш).
- **Следующие списания** — Pay с `SubscriptionId` → новый `Donation(source = RECURRING)` → общий фонд (для опеки — с `dogId`, влияет на шкалу покрытия собаки).
- **Неудачное списание** (Fail): Donation → FAILED, `failedCount++`, подписка → `PAST_DUE`, донору — письмо «обновите карту» (создаётся новая подписка с `replacesId`, т.к. сменить карту в существующей нельзя).
- **Вебхук `recurrent`** (Cancelled / Rejected / Expired): обновить статус, одно письмо донору, уведомить куратора (для опеки), пересчитать покрытие.
- **Отмена** (кабинет или токен-ссылка): сначала API провайдера, `CANCELLED` — только после подтверждения; при ошибке API — повтор через очередь. Списание, пришедшее после отмены, — автоматический возврат.
- **Смена суммы** — `updateSubscription` (`subscriptions/update`). Только для активной подписки: CloudPayments реактивирует отменённую при любом изменении ([правила](#правила-для-обработчиков), п. 12).
- **Напоминание** за 3 дня до списания.
- Согласие на рекуррент — отдельная неотмеченная галочка с суммой и периодичностью ([legal.md](legal.md)).

## Возвраты и чарджбэки

- Инициирует админ через API с ключом идемпотентности `refund:{donationId}:{n}`. Вебхук Refund → проводка `REFUND`. Ключ провайдер помнит только час ([правила](#правила-для-обработчиков), п. 10–11): возврат сначала записывается у нас.
- Откуда списывается: со счёта нужды, если она ещё не `IN_PROGRESS`/`DONE`; иначе — из общего фонда.
- Нужда в `COLLECTED`, по которой ещё ничего не купили, может вернуться в `COLLECTING` (запись в аудит и таймлайн).

## Комиссии и сверка

- **Комиссии** — ежедневный импорт из реестра провайдера как `FEE` (общий фонд → FEES_OUT). Нужды показывают валовую сумму. Опция «покрыть комиссию» добавляет к сумме доната расчётную комиссию.
- **Ежедневная сверка**: список транзакций провайдера vs наши `Donation`; пропущенные прогоняются через тот же обработчик (идемпотентно).
- **Тревоги**: ошибки вебхуков, расхождения сверки, всплеск отказов (возможный кардинг) — в админ-дашборд и уведомление сотрудникам.

## Крайние случаи

1. **Порядок вебхуков**: Pay раньше intent — создать Donation из payload; Refund раньше Pay — `DEFERRED` и повтор.
2. **Сумма в вебхуке ≠ intent** — принять фактическую, записать, пометить на проверку.
3. **Нужду закрыли, пока донор платил** — вся сумма в общий фонд, письмо с объяснением.
4. **Нужду отменили** — `CANCEL_TO_GENERAL`, бережное письмо донорам.
5. **Собаку забрали / умерла при активной опеке** — уведомить опекунов, подписка → общий фонд, если не отказались. Собаку не удалять.
6. **Возврат после закупки** — из общего фонда.
7. **Поздний вебхук за закрытый месяц** — проводка в текущем месяце с пометкой периода.
8. **Кардинг** — минимум ~100 ₽, rate limit, Yandex SmartCaptcha при всплеске отказов.
9. **Опечатка в email гостя** — повтор email в форме; поддержка находит подписку в кабинете CloudPayments по маске карты.
10. **Привязка истории к аккаунту** — только после подтверждения email.
11. **Дедлоки** — блокировки строго `Donation → Need → Subscription`, последней — блокировка периода книги ([ledger.md](ledger.md#инварианты)).
