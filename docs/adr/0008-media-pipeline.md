# 0008. Медиа: закрытый бакет, готовые размеры из воркера, отдача через приложение

- Статус: Принято
- Дата: 2026-10-11

## Контекст

Фото собак, чеки и фото результата — основа сайта. Их снимают на телефон и загружают оттуда же: файлы по 3–12 МБ, часто HEIC, с геометкой в EXIF. Требования:

- геометка и данные камеры не должны попасть к посетителям ([legal.md](../legal.md));
- чек или счёт публикуется только после того, как сотрудник отметил, что персональные данные на нём закрашены;
- картинки на публичных страницах лёгкие: LCP < 2,5 с на медленном 4G;
- загрузка 15 МБ с телефона не должна идти через процесс Next.js.

В стеке — S3-совместимое хранилище (MinIO в dev, Yandex Object Storage в prod) и sharp в воркере ([ADR-0001](0001-stack.md)).

## Решение

- **Загрузка — напрямую в хранилище** по подписанному URL (`PUT`). Тип и длина файла входят в подпись, поэтому хранилище само отклоняет файл другого типа или размера.
- **Бакет закрыт целиком.** В нём лежат оригиналы и обработанные версии; анонимного чтения нет ни у чего.
- **Версии делает воркер заранее**: четыре ширины (320, 640, 1024, 1600 px) в WebP и AVIF, без метаданных, плюс размытая заглушка. По запросу ничего не масштабируется.
- **Отдаёт версии приложение**: `GET /media/{id}/{ширина}`. Маршрут проверяет в базе, что файл обработан и публичен (фото — всегда, документ — только с `redacted`), и выбирает AVIF или WebP по заголовку `Accept`. У оригинала адреса нет.
- **`next/image` с собственным loader** строит `srcset` из готовых ширин; встроенный оптимизатор Next.js не используется.
- **HEIC превращается в JPEG в браузере** (`libheif-js` в Web Worker): в сборке sharp нет декодера HEVC.
- **S3 API — через `aws4fetch`** (подпись запросов) и обычный `fetch`, без AWS SDK.

Подробности — [architecture.md](../architecture.md#медиа).

## Последствия

- Правило «не опубликовано, пока не закрашено» — одна проверка в одном месте, и снять отметку можно сразу: следующий запрос получит 404. Ошибиться настройкой бакета и открыть оригиналы нельзя — открытых префиксов нет.
- Один адрес на ширину, лучший формат для каждого браузера: странице не нужен `<picture>`.
- Каждая картинка — запрос к приложению: чтение одной строки `Media` и поток из хранилища. Фото отдаются с `Cache-Control: immutable` на год, так что повторные запросы браузер не делает, а CDN или кеш перед приложением (задача хостинга) снимет и первые. Документы кешируются только в браузере и на 5 минут.
- Обратная сторона долгого кеша: удалённое фото (например, хозяин отозвал согласие на публикацию) сайт перестаёт отдавать сразу, но копии в кешах браузеров живут до года. С появлением CDN удаление медиа должно сбрасывать его кеш — иначе CDN продолжит отдавать файл новым посетителям.
- Набор ширин и форматов зашит в код и в уже обработанные файлы. Новая ширина — это переобработка оригиналов; для неё они и хранятся.
- Обработка занимает несколько секунд после загрузки. Пока файл не `READY`, показать его негде: форма ждёт обработки, прежде чем сохраниться.
- Собственного кода для S3 — около 150 строк; зависимость `aws4fetch` — один файл без зависимостей. Чего он не умеет (multipart, списки объектов), нам пока не нужно.
- `libheif-js` (1,9 МБ, LGPL-3.0) попадает в отдельный чанк и скачивается, только когда выбран HEIC-файл. На iPhone поле не просит HEIC в `accept`, и система, как правило, сама отдаёт сайту JPEG; декодер нужен для файлов с Android и с компьютера. Поведение iPhone на устройстве не проверялось — это пункт ручной проверки.
- В Yandex Object Storage бакету понадобится правило CORS для `PUT` с адреса сайта — при настройке хостинга.

## Рассмотренные альтернативы

- **Публичный префикс бакета и CDN перед ним.** Картинки не проходят через приложение, но документ с неснятыми персональными данными пришлось бы прятать перекладыванием файлов между префиксами: отметка `redacted` перестала бы быть единственным источником правды, а ошибка в политике бакета открывала бы файлы. Вариант остаётся доступным для фото: адрес `/media/…` можно позже направить в CDN, не меняя страниц.
- **Встроенный оптимизатор `next/image` поверх оригиналов.** Масштабирует по запросу в процессе сайта, держит кеш на диске контейнера и требует, чтобы оригинал (с EXIF) был доступен приложению по URL.
- **Загрузка через приложение** (`multipart/form-data` в route handler). Нет CORS и подписи, но 15 МБ с медленного телефона занимают соединение и память веб-процесса; прогресс и повтор сложнее.
- **AWS SDK v3.** Десятки пакетов ради пяти запросов; новые версии по умолчанию добавляют к запросам контрольные суммы, и для части S3-совместимых хранилищ это приходится отключать настройкой.
- **`heic2any`** (назван в задаче). Последний выпуск — март 2023 года, сборка libheif в нём не новее; снимок 12 Мп из 48 плиток декодировал в Chromium за 987 мс против 357 мс у `libheif-js` (версия 1.23, сентябрь 2026). **`heic-to`** — обёртка над актуальным libheif: 3,0 МБ против 1,9 МБ и 931 мс на том же снимке. Все три основаны на libheif под LGPL.
- **Конвертация HEIC на сервере.** Потребовала бы своей сборки libvips с HEVC (лицензионные ограничения) вместо готовых бинарников sharp.
