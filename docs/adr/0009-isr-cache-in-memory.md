# 0009. Кеш ISR — только в памяти процесса

- Статус: Принято
- Дата: 2026-10-11

## Контекст

Публичные страницы — ISR со сбросом по тегам ([architecture.md](../architecture.md#структура-кода)): страница собирается при первом заходе и живёт, пока server action админки не сбросит её тег. Первой такой страницей стали юридические документы (`/legal/*`).

По умолчанию Next.js пишет готовые страницы и данные `unstable_cache` на диск (`.next/server`, `.next/cache`), а время сброса тегов (`updateTag`, `revalidateTag`) держит только в памяти процесса. После перезапуска процесса — деплой, `docker compose restart`, падение — сведения о сбросе теряются, а файлы остаются, и страница, которую сбросили, но не успели пересобрать, снова отдаётся как свежая. Срока жизни у таких страниц нет, поэтому это навсегда.

Найдено ревью и воспроизведено на production-сборке: владелец публикует версию 2 политики, сервер перезапускается — `/legal/privacy` показывает версию 1 как действующую. Для оферты это значит, что донор читает один текст, а согласие записывается с другим. Вторая проблема той же природы: ответы 404 для несуществующих адресов тоже кешируются, и перебор адресов (`/legal/offer/1000001`…) пишет на диск без ограничения.

## Решение

`experimental.isrFlushToDisk: false` в `next.config.ts`: кеш страниц и данных живёт только в памяти процесса. Перезапуск начинает с пустого кеша, а не с устаревшего. Объём ограничен `cacheMaxMemorySize` (по умолчанию 50 МБ, вытесняется давно не использованное).

Настройку закрепляет unit-тест `src/lib/next-config.test.ts`: без неё ничего не падает, страницы просто начинают иногда врать.

## Последствия

- После деплоя и перезапуска первый посетитель каждой страницы ждёт её сборки. Страницы собираются из нескольких запросов к базе, это доли секунды.
- Страницы, собранные при `next build` (`/`, витрина), это не затрагивает: они лежат на диске с момента сборки и от тегов не зависят.
- **Приложение — один процесс.** При нескольких экземплярах сброс тега дошёл бы только до того, который обработал действие админки (это верно и для кеша на диске). Если понадобится второй экземпляр, нужен общий `cacheHandler` — например, на Postgres, с хранением времени сброса тегов. Это решение для задачи про эксплуатацию.
- Перебор несуществующих адресов больше не растит диск, но может вытеснять из памяти настоящие страницы. Ограничение частоты запросов — на стороне Caddy.
- Флаг экспериментальный: при обновлении Next.js сверить его в документации установленной версии и повторить проверку «сбросить тег → перезапустить → открыть страницу».

## Рассмотренные альтернативы

- **Срок жизни как страховка** (`revalidate` у страниц и `unstable_cache`). После перезапуска устаревшая страница жила бы до истечения срока и ещё один запрос сверх него; для действующей оферты и «несколько минут» — много. Рост диска от адресов с 404 не решает.
- **Рендерить `/legal/*` на каждый запрос.** Верно и просто, но проблема не в юридических страницах, а в самом приёме: её унаследовали бы страницы нужд и собак.
- **Свой `cacheHandler` с тегами в Postgres.** Правильный ответ для нескольких экземпляров; для одного процесса — лишний код и запрос к базе на каждое чтение кеша.
